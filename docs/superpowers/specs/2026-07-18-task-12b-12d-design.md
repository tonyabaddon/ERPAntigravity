## 12b — pg_restore restoration drill

**One-time drill, not recurring.** We ship daily backups but have never proven `pg_restore` works against those dump files. Untested backup = not a backup. This drill closes that gap and produces a 5-line restore runbook.

### Target environment

**Homebrew postgres@17 local** — zero cost, zero cloud data exposure, no Docker required. Postgres 17 matches production (Supabase 17.6). Standard extensions available via brew: `pgcrypto`, `uuid-ossp`, `pg_stat_statements`. Missing: Supabase-specific `pgsodium`, `vault`, `pg_graphql`, `pgjwt` — these fail during DDL restore. Workaround: restrict verification to `public.*` schema where all business data lives.

**Rejected alternatives:**
- Supabase branching (Pro-tier only, not on free plan)
- `supabase start` CLI stack (requires Docker, not installed on founder machine)
- Hosted scratch Supabase project (would expose production data to a temp cloud project — worse security posture than local)

### Steps

1. Ensure prereqs: `postgres --version` (17.x), `pg_restore --version` (17.x), `gsutil ls gs://caleo-backups-.../` (GCS auth OK).
2. Init throwaway cluster on non-default port (avoid conflict with any running postgres):
   ```bash
   export DRILL_DIR=/tmp/pg-restore-drill
   export DRILL_PORT=54329
   rm -rf $DRILL_DIR && mkdir -p $DRILL_DIR
   initdb -D $DRILL_DIR/data -U postgres --encoding=UTF8 --locale=en_US.UTF-8
   pg_ctl -D $DRILL_DIR/data -l $DRILL_DIR/pg.log -o "-p $DRILL_PORT" start
   createdb -h 127.0.0.1 -p $DRILL_PORT -U postgres restore_target
   ```
3. Pull latest dump from GCS:
   ```bash
   LATEST=$(gsutil ls gs://caleo-backups-gen-lang-client-0410251117/db-*.dump | sort | tail -1)
   gsutil cp "$LATEST" $DRILL_DIR/latest.dump
   ```
4. Restore public schema only (skip auth/vault/pgsodium — those need Supabase-specific extensions):
   ```bash
   pg_restore --schema=public --no-owner --no-privileges \
     -h 127.0.0.1 -p $DRILL_PORT -U postgres -d restore_target \
     $DRILL_DIR/latest.dump 2>&1 | tee $DRILL_DIR/restore.log
   ```
5. Capture: elapsed wall-clock time, warning count, error count, exit code.
6. Verify (compare against production rowcounts pulled fresh via MCP `execute_sql`):
   - `SELECT count(*) FROM public.tenants` → matches source
   - `SELECT count(*) FROM public.t_kasir_transactions WHERE tenant_id = '<garindo-uuid resolved from tenants>'` → matches source
   - Spot-check 3 critical tables: `products`, `customers`, `t_pesanan` — rowcount ±0
   - **Note**: `auth.users` verification skipped in this drill because Supabase's auth schema uses `pgsodium`/`vault` extensions unavailable locally. Documented in drill report + runbook caveat.
7. If any verification fails: log gap in report + investigate `backup.sh` schema scope OR `pg_restore` flags. Do NOT ship until restore actually works.
8. Tear down:
   ```bash
   pg_ctl -D $DRILL_DIR/data stop
   rm -rf $DRILL_DIR
   ```

### Deliverables

- **Drill report**: `infra/backup/drills/2026-07-18-report.md` — timeline, environment, timings, warnings, verification results, any gaps found
- **Restore runbook update**: append "Restore procedure (verified 2026-07-18)" section to `infra/backup/README.md` — the exact command sequence that worked, plus known caveats (hosted-only extensions emit warnings, `supabase start` requires Docker)
- **Cadence note**: runbook recommends re-drill quarterly OR when schema changes materially (new extensions, major table restructures)

### Rollback

Nothing to roll back. Drill is read-only against the dump file and writes to a throwaway environment.

## 12d — Rollback runbook + secret rotation doc

Two files, both live under `docs/runbooks/`. Codify what we already do; nothing new invented.

### 12d.1 — `docs/runbooks/rollback.md`

Sections:

1. **When to rollback** — decision matrix (prod broken >5min AND no fast fix → rollback)
2. **Cloud Run revision revert** — exact `gcloud run services update-traffic` command, verification steps (curl /live, check target tag)
3. **Migration revert** — `mcp__plugin_supabase_supabase__apply_migration` with the down-migration, or manual `DROP` sequence for irreversible schemas. Idempotency reminder (all our migrations are idempotent per CLAUDE.md).
4. **Frontend revert** — Cloud Build re-run against previous commit OR gcloud traffic revert. Include the tag URL smoke test after revert.
5. **Post-rollback** — log the incident in `docs/incidents/YYYY-MM-DD-<slug>.md`, notify founder, root-cause before re-attempting.

Grounded in actual events: reference Bug D (split-pool refactor rollback) and Bug E (worker rollback) from this week as worked examples.

### 12d.2 — `docs/runbooks/secret-rotation.md`

One section per secret. Each section covers: what it protects, blast radius if leaked, rotation steps, verification, re-deploy trigger.

Secrets in scope (8):

1. **Supabase service_role JWT** — `SUPABASE_SERVICE_KEY` in GCP Secret Manager. Rotate via Supabase Dashboard → Settings → API → Reset service_role key.
2. **Supabase DB password** — `supabase-db-connection-prod` + `supabase-db-connection-listener-prod` GCP secrets. Rotate via Supabase Dashboard → Settings → Database → Reset password. Update both connection URIs.
3. **GCP Service Account key** — Cloud Run runtime SA. Rotate via `gcloud iam service-accounts keys create/delete`.
4. **Sentry auth token** — CI source-map upload token. Rotate via Sentry → Settings → Auth Tokens.
5. **Resend API key** — Supabase Auth transactional SMTP. Rotate via Resend Dashboard → API Keys.
6. **Cloudflare API token** — DNS + zone management for caleo.id + caleo.web.id. Rotate via Cloudflare → My Profile → API Tokens.
7. **OpenRouter API key** — Calista LLM router (OpenRouter backend). Rotate via OpenRouter Dashboard → Keys.
8. **Google AI Studio (Gemini) API key** — Calista LLM router (Gemini backend, `DefaultCalistaAgentGemini`). Rotate via https://aistudio.google.com/apikey.

Per-secret template:
- **What it protects**
- **Blast radius if leaked**
- **Rotation steps** (numbered)
- **Where to update** (which env, which GCP secret, which Cloud Build trigger var)
- **Re-deploy after rotation** (which service needs restart)
- **Verification** (specific log line or health check that proves new secret works)
- **If verification fails** (explicit revert path: restore prior secret version in Secret Manager via `gcloud secrets versions enable`, re-deploy previous Cloud Run revision, root-cause before re-rotating)

Rollback via traffic-revert (10s) is always the primary FE recovery path; Cloud Build re-run (5+ min) is fallback if the previous revision is itself broken.

- pg_restore drill completes with matching rowcounts on target verification tables → **backup is proven restorable**
- Founder can execute rollback of a Cloud Run revision using only `docs/runbooks/rollback.md` (no verbal handoff needed)
- Founder can rotate any of the 7 secrets using only `docs/runbooks/secret-rotation.md`
- If drill fails: gap documented + fix shipped before Task 13 starts
