## 1. Problem

MSME distributor menjalankan 2+ gudang (pusat + cabang, atas + bawah, showroom + storage). Setiap hari ada perpindahan barang antar gudang via mobil / kurir. Existing feature (`WarehouseTransferModal` + `transfer_warehouse` RPC) adalah **single-shot single-SKU instant transfer**: klik → stok gudang A langsung berkurang + gudang B langsung bertambah, tanpa acknowledgment dari penerima.

Konsekuensi:
- Kalau driver bawa 500 pcs cat dan 20 pcs hilang di jalan, sistem tidak tahu. Angka jadi tidak reliable. Laporan opname mismatch.
- Fraud vector: staff gudang bisa "transfer" ke gudang lain tanpa barang benar sampai — nomor tetap balance, real inventory shrink.
- Tidak ada surat jalan resmi untuk driver.
- Legacy `atas`/`bawah` text sudah incompatible dengan `warehouses` table Phase 1-3 (configurable N-gudang).

Existing `v_pengawasan_transfer_aging` view + stub `warehouse_transfers` table sudah mengantisipasi problem ini, tapi state machine + write path belum dibangun.

## 2. Solution

Bangun **two-step state machine**: sender submit → `IN_TRANSIT` → receiver konfirmasi → `RECEIVED` / `PARTIAL` (auto-adjustment untuk selisih) / `CANCELLED` (sender cancel sebelum received). Multi-SKU per surat jalan. Pakai `warehouse_id` uuid (cutover dari legacy text). Composite PK `(tenant_id, id)` partition-ready. PDF surat jalan. In-transit visibility di StockManager. Owner Decision Inbox integration untuk stuck > 24h.

**Skip** (YAGNI untuk MSME per memory `no_approval_workflow` + `no_wa_owner_approval`):
- DRAFT state — submit langsung IN_TRANSIT.
- Dispute sebagai node state terpisah — jadi bagian PARTIAL dengan auto-adjustment.
- WA notif ke receiver — APP_INBOX bell only.
- Foto muat/turun — bukti fisik = surat jalan tanda tangan.
- Multi-hop routing (A→C via B).
- Reversal setelah RECEIVED — bikin transfer balik manual.
- Cost adjustment per warehouse — cost sama antar gudang.

## 3. State machine

```
                    ┌───────────────┐
   [initiate RPC]   │  IN_TRANSIT   │  [receive RPC, qty_diterima == qty_kirim]
  ────────────────► │  stok A: -qty │  ────────────────────────────────────────►  RECEIVED
                    │  in_transit++ │                                              stok B: +qty
                    │  stok B: 0    │                                              in_transit--
                    └───────────────┘
                            │
                            │  [receive RPC, qty_diterima < qty_kirim]
                            │
                            ▼
                       PARTIAL              stok B: +qty_diterima
                                            in_transit--
                                            + auto stock_adjustment TRANSFER_LOSS -selisih
                            
                            │
                            │  [cancel RPC, only by sender, only when IN_TRANSIT]
                            ▼
                       CANCELLED            stok A: +qty (dikembalikan)
                                            in_transit--
```

**Status enum** (canonical, replaces stub's `('initiated','received','disputed','cancelled')`):
- `IN_TRANSIT` (previously `initiated` in stub)
- `RECEIVED`
- `PARTIAL` (new, was `disputed` in stub — replaced with auto-adjustment pattern)
- `CANCELLED`

Aging view `v_pengawasan_transfer_aging` needs update: WHERE clause `status = 'initiated'` → `status = 'IN_TRANSIT'`.

## 4. Data model

### 4.1 `warehouse_transfers` (rebuild — drop stub, recreate)

```sql
CREATE TABLE public.warehouse_transfers (
  tenant_id            uuid        NOT NULL,
  id                   bigint      NOT NULL GENERATED BY DEFAULT AS IDENTITY,
  doc_no               text        NOT NULL,  -- 'TR-2026-07-012' per-tenant sequence
  from_warehouse_id    uuid        NOT NULL REFERENCES public.warehouses(id),
  to_warehouse_id      uuid        NOT NULL REFERENCES public.warehouses(id),
  sender_user_id       uuid        NOT NULL REFERENCES auth.users(id),
  receiver_user_id     uuid        NOT NULL REFERENCES auth.users(id),  -- intended receiver
  status               text        NOT NULL DEFAULT 'IN_TRANSIT',
  notes                text        NULL,
  client_request_id    text        NULL,  -- idempotency token per initiate

  initiated_at         timestamptz NOT NULL DEFAULT now(),
  received_at          timestamptz NULL,
  received_by_user_id  uuid        NULL REFERENCES auth.users(id),  -- actual receiver
  cancelled_at         timestamptz NULL,
  cancelled_by_user_id uuid        NULL REFERENCES auth.users(id),
  cancel_reason        text        NULL,

  total_qty_sent       int         NOT NULL,      -- SUM(items.qty_sent) — trigger-maintained for aging view
  total_qty_received   int         NULL,          -- SUM(items.qty_received), NULL until RECEIVED/PARTIAL
  total_loss_qty       int         NULL,          -- total_qty_sent - total_qty_received, only when PARTIAL

  created_at           timestamptz NOT NULL DEFAULT now(),
  updated_at           timestamptz NOT NULL DEFAULT now(),

  PRIMARY KEY (tenant_id, id),
  UNIQUE (tenant_id, doc_no),
  UNIQUE (tenant_id, client_request_id),  -- idempotency

  CHECK (from_warehouse_id <> to_warehouse_id),
  CHECK (status IN ('IN_TRANSIT','RECEIVED','PARTIAL','CANCELLED')),
  CHECK (total_qty_sent > 0),
  CHECK (
    (status = 'IN_TRANSIT' AND received_at IS NULL AND cancelled_at IS NULL) OR
    (status IN ('RECEIVED','PARTIAL') AND received_at IS NOT NULL AND cancelled_at IS NULL) OR
    (status = 'CANCELLED' AND cancelled_at IS NOT NULL AND received_at IS NULL)
  ),
  CHECK (
    (status = 'RECEIVED' AND total_qty_received = total_qty_sent AND total_loss_qty IS NULL) OR
    (status = 'PARTIAL'  AND total_qty_received < total_qty_sent AND total_loss_qty = total_qty_sent - total_qty_received AND total_qty_received >= 0) OR
    (status IN ('IN_TRANSIT','CANCELLED') AND total_qty_received IS NULL AND total_loss_qty IS NULL)
  )
);

CREATE INDEX warehouse_transfers_tenant_status_to
  ON public.warehouse_transfers (tenant_id, to_warehouse_id, status)
  WHERE status = 'IN_TRANSIT';  -- hot query: "in-transit to my warehouse" (receiver inbox)

CREATE INDEX warehouse_transfers_tenant_initiated_at
  ON public.warehouse_transfers (tenant_id, initiated_at DESC);  -- list ordering

CREATE INDEX warehouse_transfers_receiver_pending
  ON public.warehouse_transfers (tenant_id, receiver_user_id, status)
  WHERE status = 'IN_TRANSIT';  -- "menunggu saya" filter
```

### 4.2 `warehouse_transfer_items` (new child table)

```sql
CREATE TABLE public.warehouse_transfer_items (
  tenant_id      uuid    NOT NULL,
  transfer_id    bigint  NOT NULL,
  line_no        int     NOT NULL,  -- 1..N per transfer
  sku            text    NOT NULL REFERENCES public.stocks(sku),
  qty_sent       int     NOT NULL CHECK (qty_sent > 0),
  qty_received   int     NULL CHECK (qty_received >= 0),  -- NULL until receive RPC
  loss_qty       int     NULL CHECK (loss_qty >= 0),      -- qty_sent - qty_received, only when < qty_sent
  loss_movement_id bigint NULL,  -- FK to stock_movements.id (source='transfer_loss') if PARTIAL — per §5.2.1
  PRIMARY KEY (tenant_id, transfer_id, line_no),
  FOREIGN KEY (tenant_id, transfer_id) REFERENCES public.warehouse_transfers (tenant_id, id) ON DELETE CASCADE,
  CHECK (qty_received IS NULL OR qty_received <= qty_sent),  -- can't receive more than sent
  CHECK (
    (qty_received IS NULL AND loss_qty IS NULL) OR
    (qty_received = qty_sent AND loss_qty IS NULL) OR
    (qty_received < qty_sent AND loss_qty = qty_sent - qty_received)
  )
);

CREATE INDEX warehouse_transfer_items_sku
  ON public.warehouse_transfer_items (tenant_id, sku);  -- in-transit chip lookup

CREATE INDEX warehouse_transfer_items_transfer
  ON public.warehouse_transfer_items (tenant_id, transfer_id);
```

### 4.3 In-transit model — derived query, no separate column

Source `stock_levels(sku, from_warehouse_id).qty` **deducts at IN_TRANSIT time** (source side commits early). Destination `stock_levels(sku, to_warehouse_id).qty` **stays flat until RECEIVED / PARTIAL**.

In-transit "bucket" is **derived** per (sku, to_warehouse_id):
```sql
SELECT sku, SUM(qty_sent - COALESCE(qty_received, 0)) AS in_transit_qty
  FROM warehouse_transfer_items wti
  JOIN warehouse_transfers wt ON (wt.tenant_id, wt.id) = (wti.tenant_id, wti.transfer_id)
 WHERE wt.tenant_id = _resolve_tenant_id()
   AND wt.to_warehouse_id = $1
   AND wt.status = 'IN_TRANSIT'
 GROUP BY sku;
```

**Rationale**: computing at read-time (with the partial index above) avoids double-write to a `stock_levels_in_transit` column. Reads are bounded by the number of in-flight transfers (~5-50 per warehouse in flight at any time for MSME).

Kasir / Penjualan / Opname all read `stock_levels.qty` directly → they correctly see the source-side reduction. No phantom stock at source. Destination side shows the flat number (real committed stock only) + UI chip "+N in-transit" derived separately for transparency.

## 5. RPC contract

All new RPCs are `SECURITY DEFINER SET search_path = public`, owned by `vosi_rpc_owner`, tenant-scoped via `_resolve_tenant_id()`. Direct client writes to `warehouse_transfers` remain blocked (Phase A RLS + broken `_guard_expiry_write()` predicate — memory `guard_expiry_write_broken_predicate`).

### 5.1 `initiate_warehouse_transfer(p_from_warehouse_id, p_to_warehouse_id, p_receiver_user_id, p_notes, p_client_request_id, p_items jsonb)` returns `jsonb`

Input `p_items = [{"sku": "CAT-BIRU", "qty": 50}, ...]`.

Steps:
1. Resolve `v_tenant := _resolve_tenant_id()`, `v_sender := auth.uid()`.
2. Idempotency: if `client_request_id` already exists for tenant → return existing row (no side effect).
3. Validate: from ≠ to, both warehouses belong to tenant + active, receiver has membership + `can_receive_warehouse_transfer` permission on to-warehouse, ≥1 item, all qty > 0.
4. `SELECT FOR UPDATE` all source `stock_levels(sku, from_warehouse_id)` rows for locking.
5. Check each `stock_levels.qty >= qty` — else RAISE `TRANSFER_INSUFFICIENT_STOCK` with sku + tersedia + diminta. (Note: memory `allow_negative_stock_preorder` applies only to sales; intra-tenant transfer stays strict to avoid double-transfer race.)
6. Deduct each `stock_levels.qty -= qty` at source warehouse.
7. Generate `doc_no` via per-tenant sequence: `TR-YYYY-MM-NNN` (see §6).
8. INSERT `warehouse_transfers` (status='IN_TRANSIT', total_qty_sent=SUM). Uses `INSERT ... RETURNING tenant_id, id`; requires `t_select_own` includes `vosi_rpc_owner` (already fixed by 20261115000060 per memory `secdef_returning_gap`).
9. INSERT `warehouse_transfer_items` (line_no=1..N).
10. Log to `stock_movements` (source='transfer_out', warehouse_id=from, qty_delta=-qty, related_doc_type='warehouse_transfer', related_doc_id=transfer_id) per SKU line — reuses existing `_log_stock_movement`.
11. Emit APP_INBOX row for receiver_user_id: type='transfer_incoming', link to detail.
12. Observability: `RAISE LOG 'warehouse_transfer initiated tenant=% id=% from=% to=% items=% sender=%'`.
13. Return `{ "transfer_id": id, "doc_no": doc_no }`.

Errors:
- `TRANSFER_INVALID_WAREHOUSE` — from=to, warehouse inactive, cross-tenant.
- `TRANSFER_INVALID_RECEIVER` — receiver not member, missing permission.
- `TRANSFER_EMPTY_ITEMS` — no items.
- `TRANSFER_INSUFFICIENT_STOCK` — sku + tersedia + diminta in message.
- `TRANSFER_DUPLICATE_REQUEST` — client_request_id already used but items don't match (safety guard).

### 5.2 `receive_warehouse_transfer(p_transfer_id, p_items jsonb)` returns `jsonb`

Input `p_items = [{"sku": "CAT-BIRU", "qty_received": 50}, ...]` — must cover every SKU in the transfer.

Steps:
1. Load `warehouse_transfers` FOR UPDATE by `(tenant_id, id)`.
2. Guard: status = 'IN_TRANSIT', `auth.uid() = receiver_user_id` (only intended receiver acts; owner can force via separate `admin_force_receive_transfer` — deferred).
3. Load all `warehouse_transfer_items` for transfer. Validate p_items covers every SKU (order-agnostic match by SKU, not by position) + `0 ≤ qty_received ≤ qty_sent` per line.
4. `SELECT FOR UPDATE` destination `stock_levels(sku, to_warehouse_id)` per line.
5. For each line: UPDATE `warehouse_transfer_items` SET qty_received, compute `loss_qty := qty_sent - qty_received`. Add `qty_received` to destination `stock_levels.qty`.
6. Log per line to `stock_movements` (source='transfer_in', warehouse_id=to, qty_delta=+qty_received, related_doc_type='warehouse_transfer', related_doc_id=transfer_id).
7. If `loss_qty > 0` on any line: log a second `stock_movements` row per lossy line (source='transfer_loss', warehouse_id=from, qty_delta=-loss_qty, related_doc_type='warehouse_transfer_loss', related_doc_id=transfer_id) — pure audit label, does NOT touch `stock_levels` again (source already deducted at IN_TRANSIT). Populate `warehouse_transfer_items.loss_movement_id` with the resulting `stock_movements.id` for traceability.
8. UPDATE `warehouse_transfers` SET total_qty_received, total_loss_qty (SUM of line losses if any), received_at=now(), received_by_user_id=auth.uid(), status=('RECEIVED' if all lines full-received, else 'PARTIAL'), updated_at=now().
9. If final status = PARTIAL: emit APP_INBOX row for owners with `can_approve_adjustment` in tenant → "Selisih transfer TR-… -N pcs, cek ke gudang".
10. Return `{ "status": final_status, "total_loss_qty": loss }`.

#### 5.2.1 Loss accounting decision

**Chosen model:** at IN_TRANSIT, source `stock_levels.qty` deducts full `qty_sent`. At RECEIVE, destination `stock_levels.qty` credits only `qty_received`. Net effect: `total_stock_after = total_stock_before - loss_qty` — the loss is real inventory shrink, not a paperwork undo.

The shrink is attributed to `from_warehouse_id` (where the barang physically vanished — left source, never arrived) via a `stock_movements` row with new enum value `'transfer_loss'`, `qty_delta = -loss_qty`, `related_doc_type = 'warehouse_transfer_loss'`, `related_doc_id = transfer_id`. This row is a **pure audit label** — it does NOT re-touch `stock_levels` (source's deduction at IN_TRANSIT already committed the loss to inventory; a second deduction would double-count).

We deliberately do NOT use `stock_adjustments` for the loss row because that table likely has a trigger applying `qty_delta` to `stock_levels` (verify at implementation — memory `check_constraints_before_rpc_rewrite`). Using `stock_movements` with a new source avoids that trigger-conflict risk.

Owner sees the loss in Keputusan Owner inbox (aged rows + PARTIAL rows joined via `related_doc_id`).

**Alternative rejected:** credit `loss_qty` back to source at RECEIVE. Wrong — the barang did leave source physically; the loss belongs to inventory, not to source's paperwork.

Errors:
- `TRANSFER_NOT_FOUND` — id + tenant mismatch.
- `TRANSFER_WRONG_STATUS` — not IN_TRANSIT.
- `TRANSFER_NOT_RECEIVER` — auth.uid() != receiver_user_id.
- `TRANSFER_ITEMS_MISMATCH` — p_items doesn't cover every SKU / has extra SKU / qty_received > qty_sent / qty_received < 0.

### 5.3 `cancel_warehouse_transfer(p_transfer_id, p_reason)` returns `jsonb`

Steps:
1. Load `warehouse_transfers` FOR UPDATE.
2. Guard: status = 'IN_TRANSIT', `auth.uid() = sender_user_id` (only sender cancels; owner can force via separate RPC — deferred).
3. For each item: `SELECT FOR UPDATE` source `stock_levels`, add back `qty_sent`.
4. Log per item to `stock_movements` (source='transfer_cancel_return', warehouse_id=from, qty_delta=+qty_sent, related_doc_id=transfer_id). New enum value.
5. UPDATE transfer SET status='CANCELLED', cancelled_at=now(), cancelled_by_user_id=auth.uid(), cancel_reason=p_reason.
6. Emit APP_INBOX row for receiver: "Transfer TR-… dibatalkan sender".
7. Return `{ "status": "CANCELLED" }`.

## 11. Scale-forward architecture — IRREVERSIBLE decision memo

**Decision:** ship `warehouse_transfers` + `warehouse_transfer_items` with composite PK `(tenant_id, id)` (bigint identity), partition-ready from day one.

**Alternatives considered:**
- Single `bigint PRIMARY KEY id` (like the stub had) — rejected: cannot partition without downtime once table >10M rows.
- UUID PK — rejected: bloats indexes for high-volume append-only table, breaks natural doc-no ordering.
- `(tenant_id, uuid)` — rejected: same UUID cost + no ordering benefit.

**Consequences:**
- Blast radius if we later want single-tenant reporting across all tenants (SaaS analytics): trivial — `WHERE 1=1` still works with composite PK.
- Migration to declarative partitioning later: partition by `RANGE (tenant_id_bucket)` or `HASH (tenant_id)` — composite PK allows this without table rewrite (just `ALTER TABLE ... ATTACH PARTITION` shape).
- Migration path if we ever undo: `ALTER TABLE ... DROP CONSTRAINT` + `ADD PRIMARY KEY (id)` — costly on large table but possible.

**Scale ceiling check** (6 questions per CLAUDE.md):

| Q | Answer |
|---|---|
| **Ceiling at 10× scale (~10K tenants, ~100M rows)** | Insert throughput: initiate RPC does 1 header + N items + 2N movements = ~5 rows per transfer. At 10K tenants × 20 transfer/day = 200K transfers/day = 1M rows/day = ~365M rows/year across all transfer tables. **Breaks first:** `warehouse_transfer_items` at ~100M rows in year 1 — partition trigger. Composite PK ready. |
| **Hot path** | Receiver "menunggu saya" query: `WHERE tenant_id = X AND receiver_user_id = me AND status = 'IN_TRANSIT'`. Indexed by `warehouse_transfers_receiver_pending` partial index — cheap even at scale. |
| **Partition-ready** | ✓ Composite PK. Partition key candidate: `HASH (tenant_id, 32)` for 32-way distribution. |
| **Idempotency** | ✓ `client_request_id` unique per tenant — retry-safe on initiate. Receive/cancel not idempotent by design (status guard blocks re-entry). |
| **Long ops** | Bulk initiate up to ~50 SKU per transfer = single-row lookup + N updates + N inserts, well under 5s at any scale. Sync RPC OK. |
| **Cost curve** | Per-tenant transfer volume flat (MSME has bounded warehouses). No paid API. Storage grows linear with tenant activity. Cost flat per tenant. |

**Follow-up work spawned:**
- Partition migration when `warehouse_transfer_items` crosses 10M rows (not in this spec, follow monitoring).
- Add `admin_force_receive_transfer` + `admin_force_cancel_transfer` RPCs for owner override — deferred to Phase 2.
