4. Walk-in Tandai Lunas — Kill (bukan relokasi)

Verifikasi DB prod: 0 walk-in orders pernah ada. Fitur defer-payment walk-in nggak pernah dipakai. Daripada relokasi, hapus saja.

Query prod (2026-06-21)

SELECT sales_channel, status, count(*) AS cnt
FROM orders
GROUP BY sales_channel, status
ORDER BY sales_channel, cnt DESC;

▸ 5 orders total · 0 walk-in · 0 WAITING_PAYMENT
▸ Tidak ada data yang harus di-backfill
▸ Tidak ada user yang impact

Yang dihapus (frontend)

  • PipelineScreen.handleMarkPaid (otomatis hilang saat Pipeline dihapus)
  • orderService.markWalkinPaid di supabaseClient.ts
  • salesEntriesService.fetchOpenWalkinDrafts (sudah orphan)

Yang dipertahankan (DB)

  • RPC mark_walkin_order_paid di DB — biarkan dulu, drop di phase cleanup terpisah
  • Enum value 'walkin' di sales_channel — biarkan, low-impact orphan

Yang DICEK ulang di plan

  • Catat Penjualan flow: pastikan tidak ada UI path yang masih ngirim sales_channel='walkin' dengan status='WAITING_PAYMENT'
  • PenjualanScreen / PenjualanBaruScreen branch logic untuk walk-in mode

Kenapa kill lebih jujur dari relokasi: Data prod nunjukkin fitur ini ide bagus di kertas tapi nggak nyantol di lapangan. Customer Garindo bayar langsung di counter (atau lewat WA), bukan defer. Relokasi-untuk-relokasi cuma mindahin dead code dari satu screen ke screen lain. Hapus = lebih sedikit kode, lebih sedikit surface area untuk bug, satu modal kurang yang harus di-test.
