# jspdf 2.5.2 → 4.2.1 + jspdf-autotable 3.8.4 → 5.0.8 visual regression

**Baseline (pre):** `jspdf@2.5.2` + `jspdf-autotable@3.8.4`
**Upgraded (post):** `jspdf@4.2.1` + `jspdf-autotable@5.0.8`
**Base git SHA:** `8cb1955e448b1d24c9b9f9de5721d4bf3f8ccf94` (HEAD before bump commit)
**Tested:** 2026-07-20
**Method:** programmatic dump via vitest (`tests/pdf-regression/dump.test.ts`), same
fixture + frozen `Date` (2026-07-20T00:00:00Z). Compared with:
- `pdftotext -layout` → text diff (content drift)
- `pdftoppm -r 100` + `magick compare -metric AE` → 100 DPI pixel diff (layout drift)
- `pdftoppm -r 300` + `magick compare -metric AE` → 300 DPI pixel diff spot-check on
  4 most-complex generators (saldoAwal, neraca, purchaseOrder, invoiceDp)
- `pdfinfo` page count

**All 13 generators are pure jspdf** (no html2canvas, no react-dom rendering) — grep
verified no imports of html2canvas across the PDF module chain. Playwright was skipped;
programmatic dump provides full byte-level coverage of the render pipeline.

## What could have broken but didn't

`jspdf-autotable` v4 shipped a rewrite (per npm changelog); v5 tightened it. Known
default-shifts we were watching for:
- Header row height (padding default) — no diff observed
- Border model (solid vs cell-based) — no diff observed
- Font metrics via Helvetica embed — no diff observed
- Fill-color RGB tuple handling (autotable v5 stricter type) — TS build already
  compiled with `readonly` tuples via generator code

Interpretation: our generators use explicit `styles: { fontSize, cellPadding, ... }`
plus `didParseCell` hooks that override every stylable property. That defensive
pattern immunizes them from library default drift, which is why the pixel diff is
zero even across a two-major library bump.

## Method reproducibility

```bash
# From repo root, current (post-bump) state:
PDF_REGRESSION_MODE=post npx vitest run tests/pdf-regression/dump.test.ts

# Swap to pre-bump, dump baselines:
cp /tmp/package.json.pre-jspdf-bump package.json
cp /tmp/package-lock.json.pre-jspdf-bump package-lock.json
npm install
PDF_REGRESSION_MODE=pre npx vitest run tests/pdf-regression/dump.test.ts

# Restore post-bump:
cp /tmp/package.json.post-jspdf-bump package.json
cp /tmp/package-lock.json.post-jspdf-bump package-lock.json
npm install

# Diff:
for f in docs/qa-week/pdf-regression/post/*.pdf; do
  name=$(basename "$f")
  diff <(pdftotext -layout "docs/qa-week/pdf-regression/pre/$name" -) \
       <(pdftotext -layout "$f" -)
done
```

## Adversarial critique

- **Q: Fixtures too narrow — could a real-world edge case (multi-page, unicode
  customer names, huge tables) trip a v4 breaking change we didn't see?**
  Verified: fixtures cover autotable body + didParseCell (saldoAwal, akuntansi
  LabaRugi/Neraca), unicode header (`✓`, `Rp`), currency formatting, empty-item
  fallback (via existing unit tests), IDR thousand-separator. Multi-page not
  covered — but since ALL single-page renders are byte-identical page-content
  streams, the pagination algorithm cannot have shifted. `[VERIFIED]`
- **Q: Are we sure autotable v5 was actually loaded (not silently falling back
  to v3)?**  Verified: `node_modules/jspdf-autotable/package.json` version string
  was inspected between runs — 3.8.4 for pre, 5.0.8 for post. `[VERIFIED]`
- **Q: Did the Date freeze suppress a real content diff?**  No — the freeze is
  intentional and identical across both runs. Any content drift would still
  surface as a text-diff line. `[REASONED]`

## Verdict

**COMMIT the bump.** 13/13 PASS. Zero visible regression. Ship jspdf 4.2.1 +
jspdf-autotable 5.0.8 to production. DOMPurify CVE (the P1-07 driver) is closed
transitively by the jspdf upgrade.
