Communication Architecture: Pros & Cons

How the Go daemon, React frontend, and Supabase talk to each other

A

Go → Supabase directly + React Realtime

Go daemon writes chats/orders to Supabase → React subscribes via Supabase Realtime websocket

Pros

  • No extra server to maintain — Supabase IS the backend
  • Realtime push to frontend is built-in (no polling)
  • Single source of truth for all data
  • Supabase Auth + RLS handles access control for free
  • Go only needs 1 credential (Supabase service key)

Cons

  • Go daemon needs Supabase SDK or raw REST calls (small overhead)
  • Business logic split across Go + Supabase functions — harder to test end-to-end
  • Supabase Realtime has message size limits (~1MB) — fine for chat, bad for large file blobs
  • If Supabase goes down, everything stops (single point of failure)
✓ Best fit if you want minimal ops and your team already knows Supabase
B

Go exposes its own REST API

Go daemon runs HTTP server → React calls Go's endpoints directly → Go writes to Supabase

Pros

  • All business logic lives in one place (Go) — easy to test and reason about
  • Go controls exactly what data is exposed to the frontend
  • No dependency on Supabase Realtime — Go pushes via SSE or websocket
  • Easier to add rate limiting, auth middleware in Go

Cons

  • Go daemon must stay running 24/7 and be network-accessible to the frontend
  • React needs to know the Go server's URL — complicates deployment
  • You build your own WebSocket or SSE for live updates (not free like Supabase Realtime)
  • CORS, auth, TLS — more infrastructure to configure
  • Two things to deploy and monitor (Go server + frontend)
✓ Best fit if you want Go to be the authoritative backend and plan to grow beyond Supabase
C

Node.js API layer in the middle

Go daemon POSTs webhook events → Node.js/Express handles logic + Supabase writes → React calls Node API

Pros

  • Matches the codeSnippetNode already in your codebase — familiar pattern
  • Node.js is easier to modify quickly than Go (JS ecosystem, npm packages)
  • Good separation: Go = WA I/O only, Node = business logic, React = UI
  • Easy to add third-party integrations (payment gateways, shipping APIs) in Node

Cons

  • Three things to deploy and keep running: Go daemon + Node server + React frontend
  • Data passes through two hops before reaching the DB — more latency, more failure points
  • Two languages to maintain (Go + JS) for what is essentially a data pipeline
  • Webhook between Go and Node must be secured (shared secret, firewall rules)
✓ Best fit if you already have a Node.js team and want to keep Go responsibilities minimal

Quick decision guide:

  • Smallest ops footprint, fastest to ship → A
  • Most control over business logic, production-grade → B
  • Already have Node.js, plan to add payment/shipping integrations soon → C
