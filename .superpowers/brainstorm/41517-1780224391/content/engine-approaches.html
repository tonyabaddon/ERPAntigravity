Core AI Engine: 3 Architecture Approaches

How to structure the Go daemon, state machine, and Supabase together

A

Go-centric state machine (Recommended)

Flow: WhatsApp → Go daemon (state machine + Gemini calls) → writes to Supabase → React subscribes via Supabase Realtime
The Go daemon owns the full conversation state machine: GREETING → COLLECTING → CLARIFYING → STOCK_CHECK → CONFIRMING → BOOKED → ESCALATED
It calls Gemini for natural language, checks Supabase stock table, writes conversation + order rows directly to Supabase using the service key. React gets live updates via Supabase Realtime websocket.
Pros
  • All logic in one language (Go) — easy to debug
  • React Realtime is free — Sales Inbox goes live with no extra work
  • Daemon is already running — no extra server
  • Timeout jobs run natively in Go goroutines
Cons
  • Go daemon crash loses in-memory state (mitigated by persisting state to Supabase after every step)
  • Go team needed for changes to conversation logic
✓ Best fit: single Go developer, want to ship fast, already using Supabase
B

Supabase Edge Functions as the brain

Flow: WhatsApp → Go daemon (thin WA layer only) → POST to Supabase Edge Function → Edge Function runs state machine + Gemini → writes to DB → React Realtime
Go daemon is kept minimal: receive WA message → POST payload to a Supabase Edge Function URL → return. The Edge Function (TypeScript/Deno) handles the state machine, calls Gemini, updates the DB, and triggers the WA reply back via a Go webhook endpoint. Go only handles WA I/O.
Pros
  • Business logic in TypeScript — easier to iterate on conversation flow
  • Edge Functions scale automatically, no memory concerns
  • No state in Go — daemon crash has zero effect on conversation state
Cons
  • Two languages: Go (WA I/O) + TypeScript (logic) — split mental model
  • Edge Functions have 150s timeout — fine for chat, watch timeouts
  • Go daemon still needs an HTTP endpoint for Edge Function to send reply back
  • Supabase Edge Function cold starts add latency (~200-500ms)
✓ Best fit: want to avoid Go complexity for business logic, comfortable with TypeScript
C

Go daemon + lightweight REST API (self-contained)

Flow: WhatsApp → Go daemon (state machine + Gemini + HTTP server) → React polls/websocket Go API → Go writes to Supabase for persistence only
Go daemon runs everything: state machine, Gemini calls, and serves a REST/WebSocket API that the React frontend connects to. Supabase is used only as a database (no Realtime, no Edge Functions). Go is the single backend.
Pros
  • Truly self-contained — one binary does everything
  • No Supabase Realtime dependency — Go WebSocket is faster
  • Full control over API contract between frontend and backend
Cons
  • Must build WebSocket/SSE server in Go — significant extra work
  • CORS, TLS, auth middleware all need implementing
  • React must know Go server's IP/domain — complicates deployment
  • More moving parts to secure and maintain
✓ Best fit: want Go to be the complete backend long-term, willing to invest in infrastructure
